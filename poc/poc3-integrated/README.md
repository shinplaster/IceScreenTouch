# PoC 3: ミラーリング画面をクリックして iPhone を操作する

PoC 1（UxPlay の映像）と PoC 2（BLE HID のタッチ）を 1 つにつなぎます。

```
iPhone --AirPlay--> UxPlay (d3d11videosink のウィンドウ)  … 映像
PC のマウス → ウィンドウ上の位置を 0..10000 に変換 → BLE HID デジタイザ → iPhone  … タッチ
```

UxPlay の映像ウィンドウは UxPlay 自身が描画します。このアプリはそのウィンドウの位置・大きさを Win32 API で読み取り、マウスのボタン操作を低レベルフックで受け取って、映像の領域の内側の操作だけをタッチに変換します（ウィンドウへの描画や乗っ取りは行いません）。

## 使い方

前提: PoC 1 のビルド、PoC 2 の venv、iPhone と PC の BLE ペアリング、iPhone のズームがオン。
**パッチ入りの UxPlay**（`poc/poc1-uxplay/UxPlay/build-isr/uxplay.exe`、下記）を自動で使います。無ければ通常版にフォールバックしますが、その場合は横向きへの追従の精度が下がります。

```powershell
cd poc/poc3-integrated
.\run.ps1 -v          # -v で各タッチ操作を表示
```

1. 起動すると UxPlay と BLE HID の広告が始まります（`poc/poc2-ble-hid` や前回の起動が残っていたら、先に終了してください）。
2. iPhone のコントロールセンター → 画面ミラーリング → `iScrMirror`。
3. 映像のウィンドウが出たら、その上で操作します。

| 操作 | 動作 |
|---|---|
| 左ドラッグ | 1 本指のタッチ / スワイプ（クリックはタップ） |
| Ctrl + 左ドラッグ | 2 本指のピンチ（2 本目は画面中心に対して対称な位置） |
| `H` | ホームのジェスチャー（下端から上へスワイプ）。映像ウィンドウにフォーカスがあるとき |
| `R` | 横向きのときの回転を切り替える（90 → 270 → 0 → 180）。映像ウィンドウにフォーカスがあるとき |

- 映像の黒帯（映像の外側）のクリックは無視します。押下は映像の内側で始まったものだけを有効にします。
- 映像の外まで引きずると、座標は映像の端に固定されます。
- 画面を回転させると、ウィンドウが映像のサイズに合わせて自動でリサイズされます（モニターの作業領域の 90% が上限。`--no-follow` で無効化）。

ステータス行（変化があれば表示）:

```
[status] uxplay=up  iphone=iPhone16,1  video=498x1080(sink)  window=yes  hid_subscribed=1
[window] picture is now 1920x886; window client resized to 1920x886
```

- `video=...(sink)`: パッチ入り UxPlay が報告した実際の描画サイズ。`(log)` は通常版のログからの推定、`-` は未取得。
- `hid_subscribed=0` のあいだの操作は破棄されます。iPhone が BLE でこの PC に接続されていません。

## 実機フィードバックを受けた変更（2026-11-05）

初回の実機検証で、次の 2 点が見つかりました。

| 症状 | 原因（調査結果と仮説） | 対策 |
|---|---|---|
| 狙った位置は押せるが、クリックが反応しないときがある | **仮説**: 8 ms 間隔のポーリングだったため、BLE への送信待ちの間に起きた短いクリックを見逃していた。短すぎるタップは iOS 側でも無視されやすい | マウスのボタン操作を低レベルフックのイベントとして受け取り（見逃しゼロ）、指を最低 70 ms 押し続け、離す直前に最終位置を送り、移動は約 60 回/秒に制限 |
| 横向き（ゲームなど）でウィンドウが追従せず、座標がずれる | **確認済み**: UxPlay は映像を切り出さず、ウィンドウは回転しても形が変わらない。描画サイズが変わるのに、ログの推定値に頼っていた | UxPlay にログ出力のパッチを当て（`poc/poc1-uxplay/patches/`）、描画の実サイズを取得。ウィンドウもそのサイズに追従させる |

クリック問題は、手元で原因を直接は再現できていないため「仮説」です。ただし、遅い BLE 回線を模した状態で短いクリックを連打すると取りこぼす構造は、テストで確認できます（現在の実装では取りこぼしません）。実機で改善したか教えてください。

## 横向きのタッチ座標（実機で確認済み）

横向きのゲームを開くとウィンドウは追従しましたが、タッチの位置が縦のまま（回転していない）に感じられる、という報告がありました。デジタイザの座標が、回転後の画面ではなく**本体の縦向きを基準にしている**という仮説を立てて対応し、実機で次のとおり裏づけられました。

- ゲーム起動時の横向き: 回転 **90** で一致
- 逆向きの横向き: 回転 **270** で一致

対応の内容は次のとおりです。

- 映像が横長（幅 > 高さ）のあいだ、クリック位置を回転してから送ります。縦のあいだは回転しません。
- 回転は 4 通りです。どれが正しいかは映像からは分からないため（横向きの左右も判別できません）、設定にしています。

| 回転 | 変換（映像上の位置 (u, v)、0〜1 → 送る位置） | Safari ページで測ったときの見え方 |
|---|---|---|
| 0 | (u, v) | page_x ~ +sent_x, page_y ~ +sent_y |
| 90 | (1−v, u) | page_x ~ +sent_y, page_y ~ −sent_x |
| 180 | (1−u, 1−v) | page_x ~ −sent_x, page_y ~ −sent_y |
| 270 | (v, 1−u) | page_x ~ −sent_y, page_y ~ +sent_x |

**合わせ方（早い順）**

1. **試行**: 横向きにして、映像ウィンドウにフォーカスがある状態で `R` を押します（`[rot ] landscape rotation = ... deg` と表示）。タップが正しい位置に当たる回転を探します。iPhone を横向きのまま 180 度回すと（左右反転）、正しい回転も 90 と 270 で入れ替わります。
2. **実測**: 横向きの iPhone の Safari で、コンソールに表示された URL を開き、`probe` を実行します。9 点のタップのあと `orientation: ... matches rotation r270` のように判定が出ます。出た回転を `rot 270` で設定してください（`--landscape-rot 270` で起動時の初期値も指定できます）。`probe` の実行中はマウスに触れないでください。

**コンソールコマンド**: `rot [0|90|180|270]`、`probe`、`help`、`quit`。

## 横向きの左右の自動判別（調査結果: 判別できない）

**目的**: 2 つの横向き（回転 90 と 270）を、`R` キーなしで自動判別できるか。

**結論（2026-11-05、実機のログ 4.5 MB で確認）**: UxPlay が受け取れる情報からは、2 つの横向きを判別できません。`R` キーでの手動切り替えを前提にします。

| 調べたもの | 結果 |
|---|---|
| ストリーミング・レポート（plist、約 240 回分）の全キー | 統計値だけ（FPS、遅延、キュー、通信量など）。向きのキーはなく、`landscapeA` と `landscapeB` の差は、値の揺れの範囲に収まる |
| 180 度反転のときの新しいコーデック更新パケット | **来ない**。4 回あったのは、すべて縦 ⇄ 横の切り替え時だけ |
| 反転の直前 12 秒間のログ | 特別なイベントなし（NTP 同期などの定期的なもののみ） |
| 縦 ⇄ 横の切り替え時のヘッダー 128 バイトと SPS | 同じ向き（縦どうし、横どうし）ではタイムスタンプ以外が同一。2 つの横向きの開始時のヘッダー・SPS も同一 |
| `landscapeA` と `landscapeB` の全体比較 | 時刻、NTP、音声の量、乱数様のデータなど、向きと無関係な差のみ |

つまり、向きの情報は、暗号化された映像データの中にあるとしても、現在の UxPlay の出力には現れません。画面の中身（ピクセル）にも現れません（UI はどちらの横向きでも正立するため）。

調べていないこと: 暗号化された映像のキーフレーム（IDR）の出現タイミング。反転で出る可能性はありますが、他の理由（定期的な出力、画面の大きな変化）でも出るため、誤検出すると、手動より悪くなります。

**調べて分かったこと**

- 画面の中身（ピクセル）からは判別できません。UI は 2 つの横向きのどちらでも正立して表示され、違いは「本体がどちらへ回っているか」だけで、映像には現れないためです。
- AirPlay のセッション情報（SETUP の plist）には、向きに関するキーがありません（実際のログで確認）。
- 手がかりとして残るのは、次の 2 つです。向きの情報が入っているかは、実際に回して比較しないと分かりません。
  - iPhone が 1 秒ごとに送る**ストリーミング・レポート**（バイナリ plist。`-FPSdata` で内容を表示できる）
  - コーデック更新パケットの**ヘッダー 128 バイト**（パッチで 16 進ダンプを出す）
- 参考: UxPlay は AirPlay の機能ビット 8（画面回転に対応）を無効にしています。有効にすると iPhone の送り方が変わる可能性がありますが、未検証で、副作用も不明です。

**データの取り方（再調査したいとき）**

```powershell
.\run.ps1 --collect -v          # logs/ に時刻つきのログを保存（-FPSdata も自動で有効）
```

ミラーリングしたあと、**向きを変えて 3 秒ほど待ち、コンソールに `mark <名前>` と入力**し、そのまま 10〜15 秒待ちます（レポートは 1 秒ごと）。

| 順番 | 操作 | 入力 |
|---|---|---|
| 1 | 縦向きのまま | `mark portrait` |
| 2 | ゲーム起動時の横向き（回転 90 で合う向き） | `mark landscapeA` |
| 3 | 180 度回す（回転 270 で合う向き） | `mark landscapeB` |
| 4 | もう一度 180 度回す | `mark landscapeA` |
| 5 | もう一度 180 度回す | `mark landscapeB` |

同じ名前のラベルは、解析時にまとめて比べます。最後に `quit` で終了します。

**解析**

```powershell
..\poc2-ble-hid\.venv\Scripts\python.exe -X utf8 analyze_orientation_log.py logs\uxplay-<日時>.log --labels landscapeA,landscapeB
```

ラベルごとに値を比べ、(1) plist の値、(2) ログの行、(3) ヘッダーなどの 16 進ダンプのうち、ラベル間で違うものを表示します。**各ラベルの中では一定で、ラベル間で違う項目**が、向きの信号の有力候補です（`CONSTANT per label`）。

**結果の読み方（今回は 3 行目に該当）**

| 結果 | 次の方針 |
|---|---|
| 向きと対応する項目が見つかった | その値から回転（90 / 270）を自動設定する |
| 180 度回すたびにコーデック更新（`[video] codec packet #n`）が来る | 横向きのあいだ、そのイベントで 90 と 270 を切り替える |
| **何も違わない（今回）** | 映像側からは判別不能。手動（`R`）を前提にする（現在の状態を示す表示を追加するなど） |

## オプション

| オプション | 内容 |
|---|---|
| `--collect` | 時刻つきの UxPlay ログ（`logs/`）を保存し、`-FPSdata` を有効にする。コンソールの `mark <名前>` で目印を入れる |
| `-v` / `--verbose` | タッチ操作を 1 件ずつ表示（押下位置、押し続けた時間） |
| `--dry-run` | Bluetooth を使わず、送る内容だけを記録（UxPlay の動作確認用） |
| `--no-uxplay` | すでに起動している uxplay.exe にそのまま接続 |
| `--no-follow` | 映像サイズが変わってもウィンドウをリサイズしない |
| `--landscape-rot DEG` | 横向きのときの初期回転（0 / 90 / 180 / 270、既定 90。実行中は `R` / `rot` で変更） |
| `--probe-port PORT` | `probe` 用ページのポート（既定 8000） |
| `--uxplay-exe PATH` | 使う uxplay.exe（既定: パッチ入りの `build-isr`、無ければ `build`） |
| `--uxplay-log FILE` | UxPlay の出力を保存（不具合の調査用） |
| `--uxplay-arg ARG` | UxPlay に渡す追加引数（繰り返し可） |
| `--name NAME` | iPhone に見える AirPlay の名前（既定 `iScrMirror`） |
| `--duration SEC` | 指定秒数で終了（テスト用） |

終了時に `[summary] gestures=.. dropped=.. max_send=..ms` を表示します。`max_send` は BLE への 1 回の送信にかかった最大時間で、大きい（数百 ms）場合は BLE の接続が詰まっています。

## 既知の制約・未確認

- **横向きの左右の自動判別**: 回転の変換自体は実機で確認できました。ただし、2 つの横向き（90 と 270）のどちらかは、UxPlay が受け取る情報からは判別できません（上記）。`R` キーで手動に切り替えます。
- **パッチ入り UxPlay の実機動作**: 回転時にウィンドウが追従したことから、`sink-caps` の出力は機能していると考えられます。
- **ズーム必須**: iPhone のズームがオンでないとタッチが届きません（PoC 2 と同じ）。
- **スクロールホイール**: 未対応です。
- **PoC の構成**: `poc/poc2-ble-hid/ble_hid_poc.py` を相対パスで読み込んでいます。本体では整理し直します。
